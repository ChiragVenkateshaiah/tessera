## Overview

This page covers the structural design choices inside operating model work: how to set spans of control, how many layers a hierarchy should have, and how to choose between functional, divisional, and matrix structures. These are mechanical-sounding decisions with large practical consequences for decision speed and cost.

## When to Use It

Use once the operating model diagnostic (see overview page) has established that structural change is warranted — this page is the "how" for the structure layer specifically, not the full operating model framework.

## Framework

**Choose the primary structural axis.** Most structures organize primarily around function (marketing, finance, operations as top-level units), product/business line, geography, or customer segment — with the other dimensions as secondary. The choice should follow from where the client's most important coordination problem sits: if cross-product consistency matters most, organize primarily by function; if speed and accountability within a product line matters most, organize primarily by product.

**Set spans and layers deliberately.** Span of control (direct reports per manager) and number of layers (levels between CEO and frontline) are usually treated as afterthoughts, but they set the cost and speed characteristics of the whole organization. Narrow spans (fewer direct reports) support more oversight-heavy work but add cost and layers, which slows decisions. Wide spans reduce cost and layers but require more delegated decision authority — which only works if decision rights are explicitly designed (see the RACI/governance page), not assumed.

**Decide matrix structure carefully.** Matrix structures (dual reporting lines, e.g., a country manager reporting to both a regional head and a functional head) solve genuine coordination problems but come with real coordination cost. Use a matrix only where the coordination need is structural and durable — not as a compromise to avoid picking a primary axis.

**Design for the target state, then build a realistic transition path.** The end-state structure and the sequence of moves to get there are two different design problems — a "perfect" target structure that requires disruptive, high-risk moves in a single step is often worse in practice than a slightly less optimal structure reached through two lower-risk stages.

## Common Pitfalls

- **Uniform spans and layers across a diverse organization.** A single span-of-control rule applied blindly across functions with very different oversight needs produces both over-managed and under-managed pockets.
- **Matrix as a compromise, not a decision.** Defaulting to a matrix to avoid a hard prioritization call usually just moves the ambiguity into ongoing operations, where it's more expensive to resolve.
- **No transition plan.** A target structure without a realistic, sequenced path to get there from the current state is a slide, not a deliverable.
